# five46 AI Acceptance Check

GitHub Action for [five46](https://github.com/sekharsdet/five46). Write a
pull request's acceptance criteria in plain English, and an AI agent checks
each one against the PR's **preview deployment**, in a real browser or
against your API. You get **one PR comment** saying which criteria hold,
why each failure failed, and a **ready-to-commit Playwright spec** for every
criterion that passed.

- **Your own LLM key.** Gemini (free tier), Groq, OpenAI, Anthropic, or AWS
  Bedrock. No five46 account, no third-party test cloud: the agent runs on
  your GitHub runner.
- **Real tests out.** Every verified criterion becomes a plain Playwright
  `.spec.ts` (or `node:test` file in API mode) that you can commit and run
  without five46 or an LLM.
- **Honest verdicts.** A failure comes with what the agent saw and a
  root-cause hypothesis, kept separate from tooling problems.

## What the PR comment looks like

> An example comment. The second criterion fails because the app shows a
> generic error instead of the expected message.

---

### ❌ five46: 1 of 2 acceptance criteria failed

Target: https://my-app-git-coupons.vercel.app/cart · five46 0.5.0

| | Acceptance criterion | Result |
|---|---|---|
| ✅ | **AC1** apply the coupon SAVE10 at checkout, then confirm the total drops by 10% | verified |
| ❌ | **AC2** apply an expired coupon, then confirm the message "This coupon has expired" is shown | assertion failed |

<details><summary>❌ AC2: why it failed</summary>

```text
Assertion failed at step 4: expected the page to contain "This coupon has expired".
The page shows "Something went wrong" instead.

Root-cause hypothesis: the coupon endpoint likely returns a 500 for expired codes instead of a validation error, so the generic error banner is shown. Check the expiry branch of the coupon handler.
```

</details>

<details><summary>✅ AC1: generated spec <code>five46-agent-mf3k2.spec.ts</code></summary>

```ts
// Auto-generated by five46 test from a real agent run against https://my-app-git-coupons.vercel.app/cart
// Goal: apply the coupon SAVE10 at checkout, then confirm the total drops by 10%
// Run mf3k2 — outcome: goal-reached
import { test, expect } from '@playwright/test'

test('apply the coupon SAVE10 at checkout, then confirm the total drops by 10%', async ({ page }) => {
  await page.goto('https://my-app-git-coupons.vercel.app/cart')
  page.on('dialog', (dialog) => dialog.accept().catch(() => {}))

  await page.getByRole('textbox', { name: 'Coupon code' }).fill('SAVE10')
  await page.getByRole('button', { name: 'Apply' }).click()
  await expect(page.locator('body')).toContainText('Total: $90.00')
})
```

</details>

Generated specs, screenshots and videos are in the **five46-results** artifact of this workflow run.

## Setup

1. Get an LLM API key. [Gemini](https://aistudio.google.com/apikey) has a
   free tier with no credit card. Save the key as the repository secret
   `FIVE46_API_KEY`.
2. Add a workflow, using one of the examples below.
3. Put the criteria in the pull request description:

```markdown
## Acceptance criteria
- A valid coupon "SAVE10" reduces the order total by 10%
- An expired coupon shows "This coupon has expired" and leaves the total unchanged
```

Headings named "Acceptance criteria", "AC", "Test plan" or "How to test"
all work, as do bold or `Label:` lines. Checkboxes, nested bullets and
template comments (`<!-- -->`) are handled. Adding the section to
`.github/pull_request_template.md` makes it a habit. PRs without the
section are skipped quietly: no run, no comment.

### Test the preview deployment (Vercel, Netlify, and others)

Preview hosts report a finished deploy as a `deployment_status` event. The
Action finds the pull request from the deployed commit.

```yaml
name: Acceptance check
on: deployment_status

jobs:
  five46:
    if: github.event.deployment_status.state == 'success'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: sekharsdet/five46-action@v1
        with:
          url: ${{ github.event.deployment_status.target_url }}
          provider: gemini
          api-key: ${{ secrets.FIVE46_API_KEY }}
```

### Test an app started in the workflow

```yaml
name: Acceptance check
on: pull_request

jobs:
  five46:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
      - run: npm ci && npm run build
      - run: npm start &
      - run: npx wait-on http://localhost:3000
      - uses: sekharsdet/five46-action@v1
        with:
          url: http://localhost:3000
          provider: gemini
          api-key: ${{ secrets.FIVE46_API_KEY }}
```

### Test an API

```yaml
      - uses: sekharsdet/five46-action@v1
        with:
          mode: api
          url: https://api-preview.example.com
          goal: create a user via POST /users, then fetch it and confirm the name matches
          allow-writes: true
          provider: groq
          api-key: ${{ secrets.FIVE46_API_KEY }}
```

API mode is read-only (`GET`/`HEAD`/`OPTIONS`) unless you set
`allow-writes`, and `DELETE` additionally needs `allow-deletes`. Only point
write-enabled runs at a preview or test environment.

## Inputs

| Input | Default | What it does |
| --- | --- | --- |
| `url` | (required) | The app or API base URL to test |
| `api-key` | | Your LLM API key (for `bedrock`, the AWS region). Empty skips the check with a warning |
| `provider` | `gemini` | `gemini`, `groq`, `openai`, `anthropic` or `bedrock` |
| `goal` | | One plain-English goal. Overrides PR criteria |
| `criteria` | | Criteria to check, one per line. Overrides PR criteria |
| `mode` | `test` | `test` (real browser) or `api` (HTTP requests) |
| `model` | | Model ID override. By default five46 picks a current small model your key can use |
| `max-steps` | | Maximum agent steps per criterion (five46 default: 15) |
| `allow-writes` | `false` | `api` mode: allow `POST`/`PUT`/`PATCH` |
| `allow-deletes` | `false` | Allow `DELETE` (api) and destructive-looking clicks (test) |
| `comment` | `true` | Post and update one PR comment. `false` writes only the job summary |
| `fail-on-failure` | `true` | Fail the step when a criterion fails |
| `turnsignal-hint` | `true` | Show a one-line pointer to TurnSignal in the comment |
| `upload-artifacts` | `specs` | `specs` uploads only the generated spec files; `all` adds failure screenshots, DOM snapshots and videos; `none` uploads nothing |
| `artifact-name` | `five46-results` | Name of the uploaded artifact |
| `allow-fork-prs` | `false` | Run criteria from fork pull requests (see Security) |
| `version` | `0.5` | five46 npm version or range. Pin an exact version (for example `0.5.0`) if you want to approve upgrades yourself |
| `github-token` | `github.token` | Reads the PR and posts the comment |

## Outputs

| Output | What it is |
| --- | --- |
| `passed` | `true` when every criterion was verified |
| `criteria-count` | How many criteria were checked |
| `report-path` | Path to five46's machine-readable JSON report ([format](https://github.com/sekharsdet/five46/blob/main/docs/cli-reference.md#machine-readable-run-reports)) |

## Security and privacy

**What leaves the runner.** Only what five46 sends to *your* LLM provider:
each page's visible text and labels (in API mode, request and response
data), plus the target URL and your criteria. Nothing goes to five46 or any
other service.

**Secrets stay in the steps that need them.**
- The LLM key is visible only to the step that runs the agent.
- The GitHub token is visible only to the steps that read the PR and post
  the comment, and those steps run `five46-github`, which loads no
  third-party packages. The agent never sees the token.
- Packages are installed in a step that holds neither, with install
  scripts disabled.

**Fork pull requests are refused by default.** A fork's description is
written by someone outside your repo, and some events (notably
`deployment_status` for preview deploys) run with your secrets. So five46
skips fork PRs with a warning unless you set `allow-fork-prs: true`. Never
use `pull_request_target` with this Action: it gives untrusted fork code
your secrets.

**The PR description is treated as untrusted data.**
- It's parsed by five46 and never passed to a shell.
- Its text can't act as a GitHub workflow command, because command
  processing is suspended while the agent runs.
- It can't inject HTML, links or images into the comment.
- It can't get the agent to upload local files. The agent only uploads
  files the criteria name explicitly, and never credential files
  (`~/.ssh`, `.env`, `.npmrc`, keys, five46's own config).
- The agent has no "go to URL" action, so it can't be steered to another
  site.

**What can become public.** On a public repo, PR comments, job summaries
and artifacts are visible to anyone who can read the repo.
- Comments show each criterion, its verdict, the failure details (text the
  agent saw on your app) and the passing specs.
- URL passwords (`user:pass@`) and secret-looking URL parameters (for
  example `x-vercel-protection-bypass=…`, `token=`, `sig=`) are masked in
  comments, job summaries and uploaded files. A secret embedded in a URL
  *path* can't be recognized, so don't use URLs like that.
- Your API key and five46 login credentials are never included.
- By default only the generated spec files are uploaded. `upload-artifacts:
  all` adds failure screenshots, DOM snapshots and videos, which show
  whatever your app displayed, so only enable it when the preview shows no
  real data.
- Point the Action at preview or test environments with test data, not
  production.

**Failure modes.** If the token can't post comments (a fork, or missing
`pull-requests: write`), the result still goes to the job summary, and the
step fails only on the actual verdict.

## Cost and speed

You pay your LLM provider directly. five46 uses a small, cheap model and a
handful of calls per criterion, and Gemini's free tier covers light use.
Browser mode first installs Chromium, which takes about a minute on a
fresh runner. After that, run time is mostly LLM round-trips, so the
provider is the biggest lever: Groq is the fastest.

## Keeping the specs

Download the `five46-results` artifact, or copy a spec from the comment,
and commit it next to your other Playwright tests. If you then want to know
which tests break or go flaky across PRs, [TurnSignal](https://turnsignal.ai/?utm_source=five46-action&utm_medium=readme)
tracks exactly that (free during the beta). Turn the comment's pointer off
with `turnsignal-hint: false`.
